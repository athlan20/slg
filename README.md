# SLG

面向玩家及其自有 AI Agent 的浏览器策略游戏。项目处于第一期实现阶段：前后端已联调打通（前端 React + Rsbuild 界面走真实 WebSocket，支持会话令牌自动登录；后端含登录注册、会话令牌、Agent 信息，九种建筑的建造/升级与排队取消（一期不提供拆除）、城池改名、一键重置账号数据，资源、金币（官府）与人口的持续产出和储量上限，以及世界地图与野地占领——协议 v16：出征带任务（掠夺 plunder / 占领 occupy，缺省掠夺），野地掠夺按幸存部队负重携回地形资源（无金币）并触发 24 小时地块冷却，野地占领受官府等级上限（到达复核、超限返程），NPC 城池仅可掠夺（库存持久化扣减、不再生、金币不可掠夺），仓库防掠夺保护规则落地（4000×等级、四资源固定均分，玩家城消费方随玩家对抗阶段接入），在途 legacy attack 行军保留 v15 结算路径；斥候侦察（NPC 城池详情需侦察解锁）、行军途中撤回与自有城池间调兵，战斗为多回合推进结构（速度 / 射程 / 判定链 / 城墙，数值占位）并生成可查询战报，运行方式见 `backend/README.md`，协议文档见 `docs/agent-api.md`）。一期上线范围的「账号、Agent 与状态」「城池、建筑与经济」「世界地图、野地与 NPC」「征兵、行军与战斗」四节已实现（玩家对抗与多回合战斗的数值评审随对应阶段推进；全部数值仍为占位）。

## 目录与职责

| 目录 | 职责 |
| --- | --- |
| `frontend/` | React + TypeScript + Tailwind CSS + Rsbuild；第一版使用极简 DOM 界面，不引入 Canvas 或 2D 渲染引擎。 |
| `backend/api/` | Node.js 接入服务，采用 Fastify + `@fastify/websocket`；标准 WebSocket 是主要游戏交互通道，HTTP 按需要补充。 |
| `backend/worker/` | 独立的 Node.js 后台进程，处理建筑完成、行军、战斗等到期任务；暂不引入单独的 Web 框架。 |
| `wechat-minigame/` | 微信小游戏：网页扫码登录的“扫码器”（扫码 → 确认登录 / 绑定），附单机翻牌配对过审内容；canvas 绘制，在微信开发者工具中打开，见其 `README.md`。 |
| `backend/common/` | API 与 Worker 共用的协议约定和游戏规则；业务逻辑不应依赖具体接入框架。 |
| `test/` | 跨前后端的端到端联调测试，验证前端、API、Worker 与 PostgreSQL 协同完成的实际游戏流程；不放单个模块的单元测试。 |
| `docs/` | 分阶段设计、生成的 Agent API 文档与历史资料。 |

## 已确定的基础架构

- PostgreSQL 保存游戏权威状态，初期也承载到期任务队列；暂不引入 Redis。是否增加缓存和任务队列组件，留待实际负载评估。
- API 与 Worker 是不同进程，最终均交由 PM2 托管。PM2 管理进程，不代替任务持久化、游戏状态校验或防重复结算。
- 玩家网页和 Agent 使用相同的服务端游戏规则。WebSocket 负责连接和消息传输，操作是否合法由游戏业务层判定。
- 实时通信使用标准 WebSocket，不使用 Socket.IO 专有协议；传输载荷为 JSON。
- 前端状态管理选型 zustand。当前实现为 `useGameSession` 自定义 Hook（纯 React hooks，
  无状态库、依赖仅 react/react-dom）；引入 zustand 在下次状态层重构时落地，
  组件从 props 取数改为从 store 取数，迁移面可控。
- 当前实现是已联调的最小玩法闭环；第一期上线目标见下方范围文档。不要依据历史源码直接复制未选定的系统或推定未经确认的数值。
