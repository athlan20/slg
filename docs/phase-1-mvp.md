# 早期最小可玩闭环（已实现阶段记录）

本文件记录最初讨论并实现的最小闭环及其交接边界，不能代替现已确认的[第一期上线功能范围](phase-1-launch-scope.md)。根目录 `README.md` 记录整个项目的通用架构。

## 目标与验收

本最小闭环阶段完成下面这条完整路径：

1. 玩家通过 WebSocket 发送用户名和密码；已存在的用户名校验原密码（自动注册已随协议 v48 关闭，新账号经第三方登录 Google / GitHub / 微信扫码创建）。
2. 玩家能够在网页中查看与自己账号关联的 Agent 信息。
3. 玩家或 Agent 能发起一座农场的建造；建造进入等待状态。
4. Worker 在到期后完成建造并保存结果；在线的玩家和 Agent 都收到状态变化，消息标明最初发起者。
5. 客户端断线后按需发送对应协议号，查询当前状态或历史事件；服务端不主动补发离线消息。

本最小闭环阶段不要求其他建筑、战斗、联盟、商城、复杂地图或 AI Agent 的模型运行环境；第一期上线目标见范围文档。

## 账号与登录

- 玩家账号以用户名作为唯一登录键。已存在的用户名必须验证原密码，不能再次注册同名账号；**密码通道的自动注册已关闭（协议 v48）**——登录不存在的用户名返回 SIGNUP_CLOSED，新账号只能经第三方登录（Google / GitHub / 微信扫码）在网页上创建。
- Agent 归属于玩家账号，不能独立注册或拥有独立的游戏账号。因此，账号尚不存在时以 Agent 身份登录应失败；玩家须先建立账号。
- 同一玩家约定拥有一个 Agent，玩家和 Agent 共用用户名、密码。玩家下线后，Agent 仍可独立连接和行动。
- WebSocket 连接建立后，登录 JSON 除用户名、密码外，还包含“本次由 Agent 登录”的字段。登录成功前连接只处理登录相关消息；成功后将账号及本次声明的登录类型绑定到连接。后续业务消息不再重复发送身份类型。
- Agent 的默认委托范围是全部。之后可按业务讨论玩家可配置的授权，但本阶段不假定已实现细分权限。
- **身份边界**：在共用密码的前提下，“玩家 / Agent”是登录方自行声明、绑定于连接的来源标记，并非可独立证明的两个身份。操作记录和网页展示应保持这一含义；不能仅凭该标记实现可靠的差异化访问控制，也不能据此验证物理上只有一个 Agent 客户端。
- 实现登录时应使用安全的密码哈希保存凭证，生产环境使用加密的 WebSocket 连接；不在状态推送或日志中回显密码。

## 消息与状态变化

- WebSocket 使用标准协议，消息载荷使用 JSON。客户端通过协议号请求对应操作或数据；具体协议号及 JSON 字段命名在实现前由前后端共同约定。
- API 将每条已登录连接与其账号、声明的登录类型关联。指令归属账号；状态变化的发起者取自**发起原始指令的连接**，不是 Worker 后续执行任务的身份。
- 玩家和 Agent 可同时操作同一座城，不设置“玩家优先”或“Agent 优先”。互斥操作按服务端成功提交的先后顺序生效；后提交的操作依据最新状态重新校验，不满足条件时返回失败和当前状态。
- 在线的玩家与 Agent 均接收该账号的状态变化，消息指明发起者。发起指令的直接结果返回给该指令的发送连接；状态变化可通知同账号的其他在线连接。
- 断线重连后不主动补推历史消息。当前状态、历史事件等都是按需请求的协议：客户端发送对应协议号后，服务端再返回所请求的数据。本阶段不预设自动补读游标或全量事件回放机制。
- Agent 信息至少要能在玩家网页中呈现；在没有独立 Agent 凭证和注册资料的本阶段，可展示声明为 Agent 的连接状态及相关操作信息。名称、头像等额外资料另行设计，不伪造为已验证身份。

## 农场建造流程

1. 玩家首次进入游戏后，应有可供建造农场的初始城池和必要条件；初始资源、建造耗时与消耗数值在业务实现时确定。
2. 玩家或 Agent 通过 WebSocket 发起建造。API 按账号和城池当前状态校验请求，保存建造状态、到期任务以及原始发起者。
3. Worker 从 PostgreSQL 领取到期任务，调用共用的游戏规则推进状态并保存建造完成结果。任务机制要避免重启或重复领取造成重复完成；具体领取、重试和迁移方案在实现时确定。
4. API 获取已经提交的状态变化，通知该账号当前在线的玩家和 Agent 连接。API 与 Worker 是不同进程，不能依赖同一进程内存传递完成消息；具体的 PostgreSQL 通知或查询方式留待实现确定。
5. 前端展示农场从待建造到已完成的状态，并可在需要时按协议号主动查询最新状态或历史记录。

## 资源建筑与建造队列（协议 v3~v5 扩展，事后补记）

第一期最小闭环落地后，按后续决策把「单一农场」扩展为四种资源生产建筑并引入建造队列与等级。本节为既成事实的设计记录；数值均为占位决策（调整入口见 `backend/common/src/rules.ts` 与 `production.ts`，清单见 `backend/README.md`）。

- **四种资源生产建筑**：农田（产粮）、伐木场（产木）、采石场（产石）、铁矿（产铁）；金币不由建筑生产。
  产量 = 等级 × 每级工作人口 × 全局速率，受科技/野地/道具加成（加成系统保留乘数位、尚未上线）。
  产量按流逝时间懒结算：读取城池或扣减资源前结算到当前时刻，离线照常累积，不依赖后台定时任务。
- **单实例（与旧游戏的简化差异）**：每种建筑同城唯一，不可重复建造（重复发起返回 `BUILDING_EXISTS`）。
  旧游戏为格位制多实例、逐座升级（仅作参考）；本项目按讨论结论简化，不引入格位。
- **等级升级**：建筑建成后可升级（`UPGRADE` 指令），升级与建造共用建造队列；权威等级存 `city_buildings` 表，
  Worker 完成时写入目标等级。等级上限、升级成本/时长公式均为占位（当前：上限 10，成本 = 建造成本 × 当前等级，
  时长 = 建造时长 × 当前等级）。
- **建造队列**：1 条在建 + 最多 2 条排队（占位）；无在建立即开工，有在建入队（排队条目无到期时间），
  队满返回 `QUEUE_FULL`。Worker 在完成事务内激活各城队首并重算时间；完成与激活均经 PostgreSQL 通知 API 推送。
- 协议细节（BUILD / UPGRADE / 队列字段 / 错误码）以生成的 `docs/agent-api.md`（协议版本 5）为准。

尚未确定：各占位数值的正式评审、科技/野地/道具加成的接入方式、元宝加速（旧游戏有，本期不做）。

## 城池、建筑与经济（协议 v7/v8，对照一期范围文档实现）

按 [`phase-1-launch-scope.md`](phase-1-launch-scope.md)「城池、建筑与经济」一节扩展已实现的后端（前端联调随前端任务跟进）；
「账号、Agent 与状态」一节的能力（登录注册、会话令牌、Agent 信息、标准 WebSocket JSON 协议、
断线按需查询）此前已具备，无协议变更。人口、储量上限、黄金上限与取消返还的规则按范围文档
2026-09-27 的更新确认并已在协议 v8 落地；v9 增加一键重置账号数据；v7 曾按占位方案实现过的建筑拆除（`DEMOLISH`）
已随确认规则移除（未对外发布）。建筑成本与每级产量仍是占位数值（清单见 `backend/README.md`）。

- **九种建筑**：在四种资源生产建筑之外新增民房（人口上限）、官府（自动产金）、军营（征兵玩法
  随后续协议接入）、仓库（防掠夺保护，随战斗玩法接入）、城墙（守城加成随战斗接入）；每种同城
  限一座，建造 / 升级走既有 BUILD / UPGRADE 与建造队列；一期不提供建筑拆除。
- **开号之初**（2026-09-27 决策，注册与 `RESET_ACCOUNT` 共用 `rules.ts` 的 `INITIAL_*` 常量）：
  自带 1 级官府（开局即产金）、人口 50（无民房时上限为 0，建民房后恢复增长）、
  初始资源五项各 5000（金/木/粮/石/铁，参照旧源码首城初始化）。
- **经济结算**：官府按等级持续产金；四种生产资源各有 100/小时基础产量（无建筑也产出，
  参照旧源码产量公式；储量上限按建筑推导产量计算、不含该基础值）；人口以 10/小时线性增长到 `100 × 民房等级 × (等级 + 1)`
  的上限（无民房为 0，征兵时消耗、征兵协议后续上线）；资源、金币与人口共用懒结算（读取或
  扣减前推进到当前时刻，离线照常累积）。
- **储量上限**：粮/木/石/铁各自 = `10000 + 对应资源基础小时产量 × 100`（不含科技加成），
  黄金固定 100 万；达到上限后停止对应生产，已有超限存量不直接扣减；仓库不改变储量上限。
- **军营征兵与守城加成（v11）**：`RECRUIT` 按一期七兵种（民夫/义兵/斥候/长枪兵/
  刀盾兵/弓箭兵/轻骑兵）征募，军营等级解锁兵种；成本与人口发起时扣减，征兵队列独立
  于建造队列且排队条目可取消（`CANCEL_RECRUIT`，全额返还；征募中能否取消待定）；
  完成后兵力驻城（`city.army`）。城墙守城加成随 `city.defenseBonus` 下发（每级 +5，
  定稿），消费方是守城战斗结算（城墙位守方受击减免）。兵种战斗数值已随 v15 数值评审
  定稿（见下节），军队耗粮由协议 v14 接入（见下节末，量级评审通过）。
- **队列维护与城池管理**：`CANCEL_BUILD` 取消排队条目并按成本快照全额返还（确认规则；
  在建条目能否取消待定）；`RENAME_CITY` 城池改名；`RESET_ACCOUNT`（v9）一键把账号全部
  游戏数据重置为开号初始状态（**仅玩家连接可调用**，Agent 返回 `AGENT_FORBIDDEN`——基于
  自报 role 的协议级限制，不是可验证的安全边界；会话凭证保留、须 confirm=true、不可逆，
  事件流清空后留一条 `account_reset` 审计事件）；`AGENT_REPORT_PLAN`（v10）Agent 上报
  下一步动作与整体计划两段自报文本（仅 Agent 连接、账号最新快照、`PUSH_AGENT_PLAN` 推送、
  重置清空；展示信息，不参与游戏逻辑）。新增 `PUSH_CITY_STATE`（改名 / 账号重置）与
  `build_cancelled` / `city_renamed` / `account_reset` 事件。
- **多城边界**：数据库一直支持一账号多城；当前协议仍只操作账号的第一座城（主城）。
  城池带数字等级（`level`，恒为 1，提升条件待设计）；多城选择、占领与分城协议随世界地图玩法另行约定。
- 协议细节（CANCEL_BUILD / RENAME_CITY / RESET_ACCOUNT / PUSH_CITY_STATE、CityView 新增
  `level` / `population` / `storage` 字段）以生成的 `docs/agent-api.md`（协议版本 11）为准。

仍未定案：进行中建造能否取消、仓库防掠夺保护的比例与掠夺结算（随战斗数值评审）、
人口耗粮数值、城池等级的提升条件与作用、多城相关协议。

## 征兵、行军与战斗（协议 v13 落地，v15 规则与数值定稿）

按 [`phase-1-launch-scope.md`](phase-1-launch-scope.md)「征兵、行军与战斗」一节实现
（征兵协议 v11 已见上文；v13 补齐战斗结构与行军扩展；**v15（AISLG-2 数值评审）定稿
规则与全部战斗数值，评审记录见 [`battle-calibration.md`](battle-calibration.md)**）：

- **多回合战斗结构**（引擎 `common/src/battle-engine.ts`，规则层 `common/src/battle.ts`）：
  一维战场（长度 120）、全体兵堆按速度降序分档行动（快档先动、同速档同时结算互无
  先手差；未进射程推进 / 进射程攻击）、互斥判定链（闪避 / 格挡 / 破击 / 暴击，万分位
  概率）、伤害 = ATK×(1−DEF/(DEF+2000))（浮点，兵堆保留余伤血池跨回合累计）、城墙
  按等级对城墙位守方减伤（守城战守方**据墙待敌**：敌方逼近时原地等待、够不到且敌方
  全部驻足时出城迎击、离墙失减伤；野地遭遇战守方迎面推进）、回合上限 100 内未歼灭
  守方判攻方败，**幸存部队撤回出发城**（同回合同归于尽判攻方全灭，胜方必有幸存）。
  野地原住守军与 NPC 袭击部队为真实编成（参考战力 30 / 40 × 等级，定稿）；武将、
  科技、装备、攻城器械、城防设施不参与结算。克制关系与混编价值、验收区间见评审记录。
- **战报**：每场战斗生成一份（`battle_reports` 表，攻方或被袭击守方账号持有）——
  双方编成与损失、逐回合统计、终局原因与城墙减伤；`GET_BATTLE_REPORTS` 分页查询、
  `PUSH_BATTLE_REPORT` 生成时推送。战损不进入伤兵治疗 / 俘虏招降 / 逃兵召回（一期确认）。
- **侦察**：`SCOUT` 派斥候（行军速度 ×2）到达产出情报快照（守军构成 / 城墙 / NPC 库存 /
  占领者）——落 `march_completed` 事件（outcome=scouted）并存 `scout_intel` 表；
  GET_TILE 对 NPC 城池的详情字段改为需侦察（快照语义：未侦察为 null，重新侦察覆盖）。
  当前侦察无对抗判定（占位）；野地与玩家城池的驻军构成保持实时可见（玩家对抗阶段
  的情报规则另行设计）。
- **行军扩展**：行军时长按编队最慢兵种的速度系数折算（斥候 ×2、轻骑兵 ×1.5，占位）；
  `RECALL_MARCH` 把在途行军原地折返（同速回程）；MARCH 目标为本账号分城时为**调兵**
  （不战斗，到达并入该分城地块驻军；分城间调兵与分城发起随多城管理阶段设计）。
- 协议细节（SCOUT / RECALL_MARCH / GET_BATTLE_REPORTS / PUSH_BATTLE_REPORT、
  MarchView.purpose 新增 'scout' / 'transfer'、GET_TILE 的 npc / scoutedAt 字段语义）以
  生成的 `docs/agent-api.md`（协议版本 15）为准。

尚未定案：侦察是否引入对抗与情报时效（战斗数值与守方纯近战被远程压制的问题已随
v15 数值评审定稿关闭，见 [`battle-calibration.md`](battle-calibration.md)）。

## 军队持续耗粮（协议 v14；数值经 v15 评审通过）

按 [`phase-1-launch-scope.md`](phase-1-launch-scope.md)「城池、建筑与经济」的军队耗粮条目实现
（范围文档原列「仍待设计」，本节记录实际落地的机制；**耗粮量级随 v15（AISLG-2）数值
评审通过维持不变**——供养能力与野地收入联调结论见 [`battle-calibration.md`](battle-calibration.md)）：

- **单兵小时耗粮**：兵种表新增 `foodUse`（民夫 2 → 轻骑兵 12，参照旧源码
  `cfg_soldier.food_use` 量级）；前端征兵面板在消耗行展示「此后耗粮 N/h」。
- **净产量结算**：粮的懒结算改为净产量 = 产量 − 全军小时耗粮（其余四种资源不变）；
  全军 = 城内驻军 ×1 + 行军中（含返程）与野地驻军 ×2（旧源码 `refreshFoodArmyUse`
  同规则）。耗粮在每次结算前现查现算（`loadArmyFoodUsePerHour`），不做事件驱动缓存，
  编成变化自然生效；`production.food` 语义不变（毛产量），净粮由
  `production.food − armyFoodUsePerHour` 得出。
- **断粮语义**：粮食扣到 0 为止（钳 0、不记负债），断粮仅停止增长，部队不解散、
  无饿死 / 逃兵惩罚；耗粮属扣减项，不受储量上限的「超限存量不扣减」规则限制。
- **协议**：CityView 新增 `armyFoodUsePerHour`（协议 v14，只加不改）；前端顶栏产量行
  的粮显示净产量并在耗粮 > 0 时附「（耗粮 N/h）」明细。

## 经济与野地数值校准（协议 v19，AISLG-17/18/19/20/22）

2026-09-29 按「设计中」五项数值需求批量评审落地（决策记录与曲线见
[`battle-calibration.md`](battle-calibration.md) 末节）。数值权威出处：
`rules.ts` / `production.ts` / `world.ts` 与 Worker 的袭击间隔常量。

- **人口（AISLG-22/19）**：上限 = 50 + 100×民房等级×(等级+1)（无民房即基线 50，
  新号显示 50/50 满编，不再出现 50/0）；增速 = 10×民房等级×(等级+1)/小时
  （无民房为 0）——升民房同时改善上限与增速，从零填满上限恒约 10 小时。

## 全局时间缩放（协议 v20，AISLG-38）

2026-09-30 紧急需求：快速验证游戏节奏，全局时间参数统一缩放（默认 ×50 加速，
`time_scale=1` 恢复正常）。配置存 PostgreSQL `settings` 表（`key='time_scale'`），
API 与 Worker 双进程共享、进程内缓存 TTL 10s 刷新、**切换无需重启**；
调整入口：`npx tsx --env-file=.env scripts/set-time-scale.ts 50`（或 `1`）。

- **耗时类 ÷ scale（钳 1 秒下限，作用于任务总时长）**：建造/升级（基准 60s×等级）、征兵（基准各兵种
  单兵时长）、行军（基准 15s/格）、掠夺冷却（基准 24h）、NPC 袭击间隔（基准 120min，v21 AISLG-28 起）。
  显式验证用环境变量（`BUILD_SECONDS` 等）优先于缩放，冒烟流程不受影响。
- **速率类 × scale**：城池产出（productionPerHour 聚合出口，含基础产量 / 建筑 /
  野地加成与采集）、人口增长（growthPerHour）、军队耗粮（armyFoodUsePerHour）——
  产出与耗粮同幅，经济关系不变。
- **只作用于新增量**：新发起任务的 dueAt 与下一次惰性结算用新值；存量任务的
  到期时间不重算（需求决策，最安全路径）。
- **前后端同步**：CityView 新增 `timeScale` 字段下发当前值，前端本地折算
  （掠夺冷却剩余）改用它；agent-api 文档头部有全局说明，文档数值为未加速基准。
- **协议面**：无消息结构变化，仅数值语义随配置变化；协议版本 bump v20。

## 各目录交接边界

| 负责目录 | 最小闭环阶段交付边界 |
| --- | --- |
| `frontend/` | 使用 React + TypeScript + Tailwind CSS + Rsbuild 实现极简 DOM 登录界面、Agent 信息、农场状态和操作入口；处理在线推送，断线后按需发起查询。 |
| `backend/api/` | Fastify 标准 WebSocket 连接、首登注册/登录、协议分发、建造指令校验与保存、在线连接通知及按需查询。 |
| `backend/worker/` | 独立进程领取农场到期任务、完成状态推进，保存可供 API 通知的结果。 |
| `backend/common/` | API 与 Worker 共享的业务规则和消息/状态定义；不要在两个进程分别实现一套农场规则。 |
| `test/` | 跨前后端端到端联调，验证登录、Agent 信息展示、农场建造、Worker 到期完成、状态通知及断线后按需查询的完整流程。 |

API 和 Worker 最终由 PM2 分别托管。PostgreSQL 同时承担权威状态和初期任务队列；第一期不引入 Redis。
